Did this payment get approved?

Take a five-minute tour to see the payment flow. Then follow along in Postman when you’re ready.

A shopper pays A$24.99. Was it approved?

You’re on the merchant’s team. Your checkout has sent a payment request. You want to see the decision and confirm you’re looking at the right payment.

  1. Merchant → Gateway · POST /payments
    Submit the payment attempt.
  2. Gateway ↔ Issuer
    The card issuer decides whether to approve it. Our local demo simulates that decision.
  3. Gateway → Merchant
    Return a payment ID and the decision.
  4. Merchant → Gateway · GET /payments/{paymentId}
    Use the ID to look up that same payment.

What goes into each request?

Both calls go to http://127.0.0.1:3100, the mock gateway running on your computer.

Path/payments/payments/{paymentId}

  "amountMinor": 2499,
  "currency": "AUD",

}

The bearer token lets the merchant call the demo API. The card token selects a simulated issuer decision. Those values serve different purposes.

See the manual Postman flow

Sample walkthrough. You can read both examples without running the API.

1. Create a payment

In a blank Postman tab, select POST and paste http://127.0.0.1:3100/payments. In Body → raw → JSON, enter the body from the previous slide. Under Authorization → Bearer Token, enter demo-merchant-token and send.

201 Created
{
  "paymentId": "pay_223402da-f6a9-4504-81fa-a7217498d920",
  "amountMinor": 2499,
  "currency": "AUD",
  "authorisationStatus": "approved"
}

2. Copy the ID into a lookup

Open another blank tab, select GET and paste the full URL with the ID you just received.

GET http://127.0.0.1:3100/payments/pay_223402da-f6a9-4504-81fa-a7217498d920

200 OK
Same payment ID, amount and approval decision

201 Created means the POST recorded a payment attempt, even for a decline. 200 OK means the GET found the record. The decision lives in authorisationStatus.

Make the same flow repeatable

  1. Paste the address once. Save both requests in a collection and use {{base_url}} wherever the server address goes. An environment lets you swap that address for a different target.
  2. Pass the ID automatically. The POST’s After response script saves the new ID. The GET reads it from {{payment_id}}.
  3. Check the result. A test compares the returned ID to the one saved by the POST. Even a wrong-payment lookup can return 200 OK.
  4. Run both steps together. Collection Runner sends the POST first and the GET second. Ask AI can draft an extra decision check for you to review.

Try it yourself

Allow 30–60 minutes. Build it from scratch to see what each change does, or import the completed workflow for a quick test run.

Set up the demo on Mac or Windows
  1. Install Node.js LTS and the Postman desktop app.
  2. Open Terminal on Mac or PowerShell on Windows. Run node --version. If the command is missing after installation, reopen the terminal and try again.
  3. Type cd followed by the path to the extracted project folder in quotes. Press Enter. Run node api/server.js.
  4. When you see Demo API running at http://127.0.0.1:3100, leave that window open and switch to Postman.

Build along

  1. Try a blank GET for http://127.0.0.1:3100/payments/pay_demo_001. Then replace the ID with pay_missing and expect 404.
  2. Follow the manual POST and GET example. Try the POST without its token for 401, then add the token and resend. Use the ID from your own response.
  3. Continue to variables and checks, then run the collection.

Import the finished workflow if you want a ready-made version.

Save, reuse and check

  1. Save both requests to a collection. Set its base_url to http://127.0.0.1:3100 and use {{base_url}} in both URLs so they share one address.
  2. Use Scripts → After response on the POST to save the newly returned ID. Before request runs before the response exists.
  3. Send the POST, then look up {{base_url}}/payments/{{payment_id}}. Add the GET check to verify that you got the intended payment.
Show the ID capture and GET check

POST script

pm.collectionVariables.unset("payment_id");

if (pm.response.code === 201) {
  const { paymentId } = pm.response.json();
  if (paymentId) pm.collectionVariables.set("payment_id", paymentId);
}

GET script

pm.test("GET returns the payment created by POST", function () {
  pm.response.to.have.status(200);

  const expectedId = pm.collectionVariables.get("payment_id");
  pm.expect(pm.response.json().paymentId).to.equal(expectedId);
});

Temporarily look up pay_demo_001 with the same test. The API returns 200 OK and the test catches the wrong ID. Restore {{payment_id}} and resend.

Run both requests together

Open the collection menu and choose Run → Functional → Local. Put POST ahead of GET and start one iteration. At this stage, expect one passing test on the GET.

Review an AI-generated test

If Ask AI is available, ask it to preserve the POST ID capture and add checks for status 201 and the two expected decisions. In our first proposal, the fallback accepted any string for an unknown card token. We asked it to fail explicitly instead.

Show the finished POST script
// ── existing: clear & save payment_id ──────────────────────────────────────
pm.collectionVariables.unset("payment_id");

if (pm.response.code === 201) {
  const { paymentId } = pm.response.json();
  pm.collectionVariables.set("payment_id", paymentId);
}

// ── status check ────────────────────────────────────────────────────────────
pm.test("Status code is 201", function () {
  pm.response.to.have.status(201);
});

// ── authorisationStatus matches cardToken ───────────────────────────────────
pm.test("authorisationStatus matches cardToken", function () {
  const cardToken = JSON.parse(pm.request.body.raw).cardToken;
  const { authorisationStatus } = pm.response.json();

  const expected = {
    demo_approve: "approved",
    demo_decline: "declined",
  };

  pm.expect(
    expected,
    `Unrecognised cardToken "${cardToken}" — add it to the expected map`
  ).to.have.own.property(cardToken);

  pm.expect(authorisationStatus).to.eql(
    expected[cardToken],
    `Expected authorisationStatus "${expected[cardToken]}" for cardToken "${cardToken}", got "${authorisationStatus}"`
  );
});

Send the POST with each demo card token. Each should have two passing tests. Rerun POST then GET for three passing tests.

Move the address into an environment

Create Local Demo with base_url set to http://127.0.0.1:3100. Select it at the top right. Remove the collection copy of base_url and keep payment_id there. Environments let the same requests use different server settings.

API authentication checks the caller's credential. API authorisation controls access. Payment authorisation is the issuer's decision. APIs can also use API keys, Basic auth or OAuth 2.0. Use the scheme the API specifies.

Use a secret store such as Postman Vault for real credentials. Keep them out of exports, screenshots, Git and AI prompts.
